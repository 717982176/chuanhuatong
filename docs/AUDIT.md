# 发布前审计报告

## 1.0.1 运行问题补充 — 2026-10-04

生产诊断反馈 4 条 KV 镜像任务持续发生原生整数越界。此前的 KV 模拟没有实施原生参数的 int32 检查，4 个真实引擎用例也没有测试镜像到期参数，因此 1.0.0 的验证未覆盖这个边界。

本次在真实 KV 绑定中复现毫秒到期参数导致的同样异常；原版本在新增“四条存量记录恢复”用例中失败，修复后通过。另覆盖合法的 2038 年后秒到期、失败重试、版本竞争、坏任务隔离、备份校验后恢复和 alarm 调度。无法访问生产中 4 条记录的实际内容，不能据此断言其具体单位或来源。

1.0.1 验证结果：21 套离线回归 410 个用例通过；workerd + SQLite + KV 的 7 个用例通过；语法、凭据特征和文档链接检查以及部署 dry-run 通过。外部 Telegram 请求全部拦截，没有部署生产。

以下为 1.0.0 的原始发布审计，保留当时的范围和结果。

## 重点检查

- **权限与身份**：Webhook Secret 校验、管理端私聊限制、Mini App HMAC 与有效时间、封禁状态、输入与一次性确认失效。
- **消息与故障**：去重、发送后记录失败、已确认发送恢复、结果不明不盲目重发、相册收集和实例重建、目标联系人固定、旧快捷菜单和队列投递前封禁检查。
- **交互体验**：欢迎与指令清理、原菜单更新、搜索词清理、联系人分组与分隔移除后合并、快捷回复记录、分页和昵称链接。
- **编辑与内容**：文本 / 图片原位同步、不可编辑转发回退、原作者与原有按钮保留、emoji 与长 HTML 边界、损坏历史记录容错。
- **数据维护**：联系人资料与最近记录分离、待回复新增 / 完成 / 超期处理、分段索引、备份大小和条目限制、预览确认与原子恢复、失败 KV 镜像轮换。

压力型模拟包含 300 位联系人各 1000 条待回复和超过 500 位联系人的分段索引；它们检查记录大小、清理快照和新留言保留，不代表实测生产吞吐量。

## 本次发布整理

1. 移除测试对旧版本源码目录的依赖，统一从当前仓库入口加载，保留有效回归检查。
2. 公开配置仅保留占位 KV ID；实际配置、本地凭据、生成物、日志和备份不纳入版本管理。
3. 增加固定开发依赖、锁文件、独立检查 / 测试执行器和本地运行引擎检查。
4. 提供读取本地环境的 Webhook 脚本，使用 POST，启用编辑订阅，不打印秘密或远端错误正文。
5. 补齐部署、升级、维护、恢复、架构、开发、安全和贡献文档，加入问题 / PR 模板及 CI。
6. 按作者选择添加 GPL-3.0-only 许可证和版权信息。

## 已知边界与上线验收

- 无用户名昵称跳转、原生编辑标记、消息删除时限、原生转发编辑及验证窗口关闭依赖 Telegram 能力与客户端，见[架构与边界](ARCHITECTURE.md)。
- 自动气泡合并依赖有限的已记录历史，无法观察客户端手动删除或推断全部历史消息。
- 单个 Bot 的请求串行协调，慢外部接口和突发生产负载可能增加等待；本次没有生产压测。
- Telegram 发送没有业务幂等键，网络结果不明时仍需要管理员核对记录。
- 依赖审计只反映检查当时数据库中已知漏洞；凭据特征检查也不是对所有秘密的完备检测。

上线应执行[部署验收](DEPLOYMENT.md)，至少检查验证后立即发送、两位访客交替消息、气泡合并、文本 / 图片编辑、搜索清理、快捷回复记录和备份恢复。GitHub 发布与实际 Worker 上线是两个步骤，仓库 CI 不会替部署者修改生产。
